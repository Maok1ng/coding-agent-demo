# 上下文压缩与工作代码

压缩需要减少完整请求的规模，也要让模型继续理解正在修改的代码。本项目将系统提示词、实际工具、
历史和输出预留放进同一个预算，再附加有界代码工作集。工作集保留实际读取过、版本仍有效的代码片段；
完整工具输出和历史仍照常归档。

## 处理流程

```text
每次 AgentRunner.run 创建独立 CodeWorkingSet
  → read_file 成功：记录实际返回的片段、范围和读取时 SHA256
  → ToolRuntime 确认工具成功后登记
  → 本次模型请求构建一次 system 与过滤后的 tools，同时用于计数和发送
  → 预留输出、协议空间，移除旧工作集标记
  → 接近软阈值且有足够可压缩历史时提前压缩；超过硬预算必须压缩或明确停止
  → 当前用户输入与近期工具配对原样保留，旧历史先归档，再机械整理或生成模型摘要
  → 核对本实例已成功读取文件的当前版本
  → 在完整请求的剩余 token 预算内选择片段或路径提示
  → 最多附加一条普通背景消息
  → 重新检查总预算，通过后才能请求模型
```

`prepare()`、手动 `compact_history()` 和 API 超限后的 `reactive_compact()` 都使用同一份工作集。
登记、版本比较和选择不调用模型；旧历史优先机械整理，必要时才生成模型摘要。
不增加索引线程、长期代码缓存或另一套 Agent 循环。

Runner 配置完整预算后，使用上述保护当前消息的路径，不再无条件执行按 50 条消息裁剪、
再缩短工具结果的旧四步流程。未调用 `configure_budget()` 的独立 `ContextCompact` 调用，
继续兼容原来的历史预算和四步接口，便于已有低级调用与测试迁移。

## 近期段的切点

近期段从历史尾部向前累计估算 token，不再固定留下 46 条消息。默认保留预算为历史可用预算的一半，
上限 8,000 tokens；独立调用 `snip_compact(..., keep_recent_tokens=...)` 可以指定近期预算。
该兼容接口仍在消息超过 50 条时才考虑归档，小消息全部能放下时不会为凑条数强行裁剪。
主 Runner 根据完整请求预算触发压缩，近期段使用同样的 token 选取逻辑。

切点尽量向前对齐最近的真实用户消息，允许最多约 20% 的跨度余量。
过长的工作跨度可以拆分成旧历史摘要与近期原文，不为了对齐而保留整个超长回合。
同一工具批次的调用与结果始终一起保留；当前请求和本轮带宿主 ID 的纠偏另行保护，
不能因 token 切点落在较后位置而被省略。手动压缩保留较小的近期段，但仍遵守这些保护。

## 迭代摘要

最终摘要优先尝试机械整理。只要发生条目内部截断或预算遗漏，就回退到模型摘要，
不能把被裁掉的历史用户限制当成已经保留。已有宿主摘要作为历史背景展开，避免重复包装和转义。
只有格式正确且引用本工作区真实归档文件的宿主摘要才会展开；真实用户标记的消息不按旧摘要处理。

机械摘要将旧摘要正文及未重复的旧请求放在最前面，不占新 user/action 条目的预算，
因此不会因新消息过多而先省略早期限制。模型摘要将旧摘要作为独立的参考输入，
明确要求整合新历史、保留用户限制、早期决定、文件状态和真实检查结果，并根据新证据更新过时事实。
旧摘要正文不进入 system 指令，也不能授予执行权限。

摘要助手有独立的完整请求预算。缩减输入时只缩减新历史，旧摘要不会被截断；
连旧摘要和必要包装都放不下时，明确报告预算不足。主请求尚未超过硬预算时可以延后提前压缩，
硬预算下则停止，不重复提交超限请求。

文件工具的代码正文由工作集负责版本校验与保留，机械摘要只保留操作、路径和结果线索，
不再复制一份未经核实的代码；完整原文仍在归档中。

## 记录什么

每次读取成功时，`ReadOutput` 携带该次实际返回内容对应的路径、行号范围与整文件 SHA256。
Runtime 只在成功的工具结果后登记，失败或被拒绝的读取不进入工作集。
保留的是模型当时实际看到的有界输出，不把压缩时重新读取的正文冒充旧工具结果。

同一路径保留最新快照，一个实例最多记录 20 个文件。主角色和各次子角色运行分别持有工作集，
不因为共享 `RunContext` 就复制所有角色读过的代码。子角色仍通过结构化摘要与证据引用交接。

快照使用读取当时的 SHA256，不用稍后的 `context.versions` 反推旧内容版本。
`context.versions` 也会在成功编辑后更新；把它套到更早读取的代码上，会错误地把旧代码认成新代码。

## 哪些代码会保留

| 当前情况 | 工作集提供的内容 |
| --- | --- |
| 快照版本与当前文件匹配 | 当时实际展示过的代码片段和范围 |
| 同一份完整读取结果仍在消息中 | 不重复附加正文 |
| 文件已变化、删除、过大或无法安全确认 | 路径、旧行号范围和需要重读的提示 |
| 预算不足以放入代码 | 简短路径提示，或省略较旧记录 |
| 来自旧会话或上一轮的工作集 | 未验证的路径线索，不恢复旧正文的有效性 |

版本比较只针对当前实例已经通过成功工具读取登记的路径，不扫描新文件。
宿主可以读取这些文件的字节计算哈希，但不会把新的文件正文自动返回给模型。
越界、符号链接或无法读取等情况不能通过降级绕过；对应快照退化为重读提示。
取消信号继续生效。

编辑、Shell、子角色和用户都可能改变文件。发现版本不匹配时，不尝试依据旧片段猜测当前代码，
也不自动把某次测试或报告当作新代码证明。必要时可以附上已读片段中的历史声明线索，明确它仍需核实。
模型应通过正常的 `read_file` 工具读取需要的行范围，再继续判断或编辑。

## Token 预算

上下文规模用保守估算 token 统一计量（见 `runtime/tokens.py`）：ASCII 按 3 字符/token，
UTF-8 多字节按字节加罚。这不是精确计数，API 超限后的补救（reactive_compact）仍然保留；
真实消耗以模型响应的 usage 为准，回合结束时汇总展示（含缓存命中率）。

| 项目 | 上限 |
| --- | --- |
| 单次角色运行记录的文件快照 | 20 个，同一路径保留最新一次 |
| 单条工作集展示的文件 | 8 个 |
| 每个文件展示的代码 | 约 3,000 字符 |
| 工作集序列化后新增内容 | 4,000 token，并受当前上下文剩余空间限制 |
| 完整请求预算 | 16,000 token（`config.json` 的 `context_token_limit` 可覆盖，最小 1000） |

这些上限同时生效，因此 8 个文件不代表能各自展示同样的代码量。
当前请求、新工具结果和必要历史优先；工作集使用剩余空间，不为保留代码挤掉它们。
若原消息已经过大，先压缩可处理的旧历史，工作集不能继续扩大超限内容。
中文等多字节文本按加罚估算会明显偏大，属于有意保守：宁可提前压缩，也不把超限留给 API 报错。

Runner 中的 `context_token_limit` 现在限制完整请求，而非只限制 `messages`：

```text
可用历史预算 = context_token_limit
              - 本次 system 与实际 tools 的估算
              - max_tokens 输出预留
              - 128 token 协议余量
```

计数会先应用与真实请求一致的文本块和缓存标记格式。历史中每条字符串转成 `text` 块的开销也计入，
不会因为短消息很多就漏算；128 的余量用于其他协议字段，不代替这些逐条封装的计数。
工具较少的角色因此拥有更多历史空间。`max_tokens` 不会为迁就上下文被静默降低；两个配置都要求真正的整数，
不接受字符串或布尔值。默认 16,000 是本项目的本地策略值，不是对模型容量的自动识别。

通常在完整预算约 80% 时考虑提前压缩。若固定提示词、输出预留或受保护消息已经占据软阈值，
压缩也无法腾出目标空间，就延后到硬预算处理，不会每次工具调用都重新总结同一份历史。
压缩后需有足够的新历史增长才再次尝试；空闲缓存窗口只做机械整理，不为窗口猜测额外请求摘要模型。
缓存标记不保证命中，供应商实际 token 数与缓存命中仍以 API usage 为准。

主 Runner 的自动与 API 超限补救按 token 选取近期段，并扩展边界保留整批工具调用及结果；当前用户输入无论多早都完整保留。
显式手动压缩保留当前输入和 token 近期段中最后至多 2 条消息，再补齐整批工具配对及本轮纠偏，
让更早已经读过的代码可以归档并由工作集复核。未配置完整预算的旧 `reactive_compact` 接口仍兼容约 5 条的保留方式。
受保护消息本身过大时明确停止，不能通过截断当前用户输入或最新工具结果来假装装得下。

摘要助手也受相同的总预算限制，独立计入其摘要系统提示词、输入封装和 2,000 token 输出预留。
旧历史先完整落盘；摘要助手输入过长时只对这部分已归档的旧历史保留头尾，当前用户输入和近期工具批次不参与有损摘要。
助手请求本身装不下、或生成的摘要仍超硬预算时明确报告预算不足。软阈值提前压缩遇到助手预算不足，
可以继续发送仍在硬预算内的原请求。固定提示词加输出预留本身就超预算时，不发主请求或摘要请求。

预算不足的运行记录提供总上限、固定开销、输出预留、协议余量和可用历史预算，便于区分是历史太长还是工具/提示词占用过大。
手动压缩、自动压缩与一次 API 超限补救均使用当前请求的有效历史预算；会话恢复不继承这份临时预算或延后标记。

## 浏览器截图

MCP 返回的图片在入口校验并等比缩小后，以 `tool_result.content` 内的独立 `image` 块传给模型，
不使用 Base64 字符数估算文字 token。每图保守预留 2,048 token；这是本地预算，不代表供应商实际计费。
整份历史发出前最多保留最新 8 张、编码数据合计 16 MiB 的图片，较早图片改为明确的省略说明，
已有截图文件引用仍保留。消息、工具调用和结果顺序不变。

当前尚未读过的截图保持完整；较早图片随旧历史归档。机械摘要与摘要助手只接收文字和图片占位，
不会把 Base64 复制到摘要，也不能凭占位描述画面或宣称视觉验收通过。再次检查画面时应重新截图。
当前输入或近期图片批次仍超出有效 token 预算时，照常明确停止，不静默降低输出预算。

## 重复压缩与工具协议

工作集用一条普通 `user` 背景消息提供，并明确是代码参考，不是新的用户命令、权限或工具结果。
它不伪造 `read_file` 调用，也不合成 `tool_result`，原有工具调用与结果仍保持配对。

每次重建前移除旧工作集标记，避免反复压缩后叠加多份相同代码。
旧代码是否仍有效需要重新核对；工作集标记本身不是新的读取证据。
完整原始历史和工具输出仍保存在 `.transcripts/`、`.task_outputs/`，不会因为保留工作集而删除归档。

## 会话恢复与权限

恢复只加载历史，等待真实用户输入，不自动恢复旧任务或工具执行。
旧工作集即使保留在 Session 中，也只提供未验证的路径和范围线索；不对未知旧标记自动读取文件计算哈希。
开启下一次 `AgentRunner.run` 时使用新的独立工作集，不能把上一次运行的快照当成本次成功读取。

工作集不会回填 `context.versions`，不恢复审批，不改变角色或 Plan 权限，也不是测试通过的证明。
恢复后修改已有文件仍须先走正常读取，遵守现有的读取版本和并发修改检查。
工作集中的代码同样属于不可信仓库内容，不能作为宿主指令执行。

## 借鉴来源

参考 Freebuff 固定提交 `e98f7304b8ed55d63662f0bb4cb477afe2636de6` 的
[compaction-working-set.ts](https://github.com/CodebuffAI/freebuff/blob/e98f7304b8ed55d63662f0bb4cb477afe2636de6/packages/agent-runtime/src/compaction-working-set.ts#L1)：
保留最近的文件读取，为未保留正文的文件留下短线索，并限制工作集预算。

本项目按现有 Python 工具与会话实现适配，增加实际读取时的版本记录、哈希复核及保守恢复边界。
没有照搬 Freebuff 的消息协议形状、模型预算或 Token 数值；保留一次 API 超限补救和旧低级压缩接口，
Runner 统一使用完整请求预算路径。
