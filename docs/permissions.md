# 操作审批与流式输出

审批级别与角色权限、Plan 是不同的开关：角色决定“能不能使用工具”，审批决定“使用前是否问用户”。
调用顺序是：角色与模式校验 → 参数校验 → 三级审批 → Hook → 工具 → 保存证据。
Hook、工具结果、项目规则、记忆和子角色都不能代替用户切换审批级别。

## 三个级别

| 模式 | 行为 |
| --- | --- |
| `ask` | 每次模型工具调用均询问，包括读取、编辑、Shell、派发和 MCP；`ask_user` 本身直接提问，不再先询问能否提问 |
| `auto`（默认） | 宿主规则自动批准常规操作，高风险或不能分类的操作交还用户；不额外调用审批模型 |
| `full` | 用户明确选择后跳过操作确认，但不是授予新角色、解除 Plan 或关闭所有保护 |

`auto` 自动批准工作区普通文件读写、固定只读 Git 查询、角色调度，以及有限的常规检查命令，
例如 `pytest`、`python -m unittest`、`npm test`、`cargo test` 和单个 `make test`。
Git 写操作（如 push/reset/clean）、删除、安装软件、任意脚本、未知 Shell、
含命令连接/替换/重定向的 Shell 都会询问。敏感文件、规则、CI 和运行记录的修改也会询问。
`read_url`、`list_symbols`、`find_symbol`、`verification_status` 属于固定只读工具；`auto` / `full`
无需人工批准，`ask` 仍逐条确认。网页不能附带任意请求头或访问私网，符号定位不获得编辑前的读取版本。
这不是完整 Shell 解析器：无法明确匹配就询问，不通过不断扩大黑名单来保证安全。

测试和构建会执行仓库代码，可能写文件、访问网络或调用其他程序。
“常规操作自动批准”只是一种便利策略，不证明命令无副作用；不信任的仓库应使用隔离环境。
**本机 Shell 的 cwd 不限制其文件系统访问。** 文件工具的工作区边界仍有效，但不是 Shell 沙箱。
Docker 也只隔离 Shell，不隔离宿主文件工具、Git 查询和 MCP。

固定只读 Git 查询每次都重新检查当前生效的内容过滤器，并禁用这些过滤器，
不缓存这项安全检查。工作区是仓库子目录或 worktree 时，也不能因配置缓存漏检而执行过滤命令。

三档都保留已有的危险命令硬性拒绝策略；`full` 也不能直接执行被该策略拒绝的命令。
这份拒绝列表只是补充防护，并不能识别所有等价写法。

MCP 的工具白名单、只读分类仍先于审批：`full` 不能让只读角色调用写型 MCP。
`auto` 继续尊重宿主 `auto_approve`；未免确认的 MCP 操作和启动 stdio 外部程序需确认。
`ask` 比 MCP 免确认列表更严格，`full` 则可以跳过 MCP/stdio 的确认；外部程序仍运行在宿主。

## CLI 和配置

```bash
coding-agent --workspace /path/to/project --approval-mode ask
coding-agent --workspace /path/to/project --approval-mode auto
coding-agent --workspace /path/to/project --approval-mode full
coding-agent --workspace /path/to/project --no-stream
```

```text
/permissions          查看当前级别
/permissions ask      逐次询问
/permissions auto     规则审批
/permissions full     跳过操作确认
```

默认来自宿主模型配置 `approval_mode`，未设置时为 `auto`。
`AGENT_APPROVAL_MODE` 覆盖宿主配置，CLI 的 `--approval-mode` 优先设置该环境覆盖值。
运行期间只接受当前真实用户输入的 `/permissions` 命令，不从普通文本里猜测升级权限的意图。

每次人工确认只批准这一条调用，不缓存同类操作批准。批准/拒绝和策略理由写入
`.task_outputs/runs/<turn-id>/*-approval.json`；Esc、Ctrl+C、EOF 不会被视作同意。
批准之前仍没有执行工具；返回后还会检查本轮是否取消。
宿主会话落盘、执行证据、压缩和记忆等内部维护不属于模型工具调用，不逐次弹确认。
`/memory forget` 等明确用户命令沿用自己的权限检查，不因为 ask 重复询问同一个用户命令。

`/permissions` 的运行时设置和单次批准不写入会话，不从历史恢复。
恢复使用本次启动的宿主配置（若明确传入 full，仍是 full），不改变 Plan 恢复时重新确认的规则。

## 文件修改预览

`write_file` 和 `edit_file` 先在内存生成候选修改与 diff，通过读取版本、唯一匹配、
工作区边界和大小检查后，CLI 展示“修改预览 · 未写入”。此时目标文件和它的父目录尚未被创建或修改。

- `ask`：先看 diff，输入 `y` / `yes` 后应用这份候选。
- `auto`：普通文件展示后按规则自动应用；敏感文件仍等待你确认。
- `full`：展示后自动应用，原有角色与 Plan 限制仍生效。

批准绑定本次候选的目标和内容，不会重新计算出另一份修改再执行。确认期间若原文件被修改、
删除、新文件被提前创建，或路径链接指向发生改变，写入会失败，需要重新读取并生成候选。
拒绝、Esc、Ctrl+C 或退出不会应用候选；一次批准也不会供下一次工具调用使用。
保存仍是乐观版本检查和原子替换，不是其他程序共同遵守的文件锁。

终端预览最多 12,000 字符和 120 行；截断时显示完整 diff 的记录路径。
完整 diff、修改前后摘要保存在 `.task_outputs/runs/<turn-id>/*-file-change.json`，
相应审批记录引用它。拒绝后的候选记录也保留，文件内容不会因为有记录就被应用。
这些记录可能含用户代码，沿用运行记录的隐私和忽略规则。

这项预览覆盖内置文件写入与编辑工具；Shell 和 MCP 沿用各自的操作确认，无法提前生成它们所有副作用的 diff。
它不提供整个任务的批量提交、撤销或会话恢复后待审批候选的重放。

## 真正的流式输出

默认 `stream: true`，通过 SDK `messages.stream()` 消费 SSE 的文字增量，CLI 实时刷新。
主角色、子角色均显示角色标签；回合结束后不重复打印已经展示的同一段最终回复，
但资源清理阶段追加的警告仍显示。控制字符会过滤，不能用模型文字移动终端光标或清屏。

仅文字增量用于显示，不展示原始工具参数片段或隐藏推理。
宿主确认收到 `message_stop` 结束标记后，才使用 SDK `get_final_message()` 的完整工具参数，
再进入原来的权限/审批/执行流程。连接提前 EOF 不能当成完整响应；达到输出上限也不执行该响应的工具。
工具不会在 JSON 参数只到了一半时执行。

Esc / Ctrl+C 会取消 SSE 请求并等待响应关闭。
模型连接池在同一 Turn 内复用，全部模型请求（包括记忆提取）结束后统一关闭，随后才交付最终结果。
关闭失败会阻止宣称成功；关闭期间中断也要保存历史、暂停未完成 Goal 并撤销 Plan 批准。
若回复未完整接收，会话与角色记录只保留已显示的文字和“不完整”标记，不保存半份工具调用，
不执行该响应中的工具，也不自动重试有歧义的响应。此前已经完成的工具仍保留真实结果。
记忆选择、提取、压缩和 Goal 验收的内部请求不展示为用户回答。

宿主模型配置设置 `stream: false`，或启动加 `--no-stream`，可关闭流式展示。
不支持 SSE 的兼容接口应显式关闭；不会在已输出一半后静默重发请求。
注入自定义 `model_call` 的测试/适配器继续使用原接口，不自动传入增量回调。

SDK 用法参考 [官方 Python SDK 流式辅助接口](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python#streaming-helpers)。
