# 代码检查点

代码检查点记录本会话中由 `write_file` / `edit_file` 修改的文件版本，让用户能够撤销最近的修改，
或选择明确的历史版本。它与对话历史分开保存；恢复代码后聊天仍保留。

## 使用

```text
/checkpoints     列出编号、父检查点、时间、摘要和当前版本
/undo            撤销最近一个 Agent 修改回合
/restore C1      恢复到 C1 完成后的受跟踪文件版本
```

一次真实用户请求构成一个 Turn。该回合内多次模型调用，以及所有串行子角色的文件修改共享一个检查点。
只读任务、拒绝的候选修改、没有落盘的操作不生成代码检查点。
同一文件在回合内修改多次，撤销时恢复到首次修改前，而不是倒退一个工具调用。
中断或失败前已经落盘的修改仍保留检查点；Esc / Ctrl+C 本身只停止执行，不自动回滚。

例如：

| 检查点 | 修改 | 恢复含义 |
|---|---|---|
| C0 | 文件首次纳入跟踪时的基线 | 恢复这些文件的原始基线 |
| C1 | 增加登录功能 | 保留登录功能 |
| C2 | 增加参数校验 | 保留登录与参数校验 |
| C3 | 调整样式 | 当前受跟踪版本 |

在 C3 输入 `/undo` 回到 C2；输入 `/restore C1` 则撤回 C3、C2 的文件变更。
检查点编号以本会话实际列表为准；有外部修改基线时，也会占用新的编号。
C0 是按需保存的文件基线，不代表启动时已经复制整个仓库。

## 预览、确认和冲突

恢复命令由宿主处理，不是模型工具，不请求模型，也不自动恢复旧 Goal。
先计算当前文件到目标文件的 diff，展示候选修改；随后列出目标检查点和涉及文件，等待真实用户确认。
拒绝确认不改变文件或当前检查点。即使宿主审批模式为 `full`，主动恢复仍要求这次确认。
Plan 模式只允许 `/checkpoints` 查看；先使用 `/execute` 切换到执行模式，才能恢复文件。

确认前后都会核对文件内容、权限和存在性。文件后来被手动修改、替换为链接，或快照损坏、路径越界时，
恢复会停止并提示问题，不提供强制覆盖选项。
已有文件恢复保存的内容和权限；检查点后通过文件工具新建的文件，在撤销时删除。

多个文件先统一核对，再逐个替换。写入中途失败会尝试恢复已改文件；仍无法安全恢复时，
锁定后续自动恢复并提示检查日志。最终提交检查点状态或同步磁盘时出错，文件也可能已经全部恢复，
不会把异常当成“没有发生修改”。之后 `/checkpoints` 只核对日志与文件、补齐可确定的元数据，
不重新执行文件修改；状态不一致时明确停止。以上是有日志的恢复流程，并非整个目录的原子事务。

已跟踪文件在两轮之间可能被用户、Shell 或其他程序修改。下一轮文件工具修改前，宿主会先保存一个
标明“外部修改”的基线，再记录 Agent 本轮修改。`/undo` 只撤回 Agent 本轮，保留该外部基线。
当前已经处于外部基线时，继续 `/undo` 会拒绝；如果确实需要撤回外部修改，必须用 `/restore C编号`
明确选中旧版本并再次审阅 diff、确认。没有进入跟踪范围的其他文件不会因此获得快照。

## 恢复后继续开发

恢复到 C1 后再次请求修改，会生成以 C1 为父节点的新检查点；编号继续增长，不覆盖原来的 C2、C3。
旧分支仍可在列表中查看，并可显式恢复。跨分支恢复会沿共同祖先计算需要撤回和重做的文件变更，
同样执行冲突检查与确认。

恢复成功后，宿主向聊天追加运行通知，说明代码已切换到哪个检查点。
原来的模型回答和测试输出仍是历史，不能当成恢复后代码的最新验证；下一次修改前需要重新读取和检查。
待回答问题和旧执行批准失效，未完成 Goal 暂停，等待用户下一条输入。

## 数据范围与存储

检查点位于 `<workspace>/.task_outputs/checkpoints/<session-id>/`，记录修改涉及文件的前后内容、权限、
存在性与哈希，以及回合、时间、摘要和父节点。目录与快照仅当前用户可读写，不是加密存储。
同一会话恢复后沿用这些记录；旧会话没有检查点时，不从历史工具调用重建或重放。
保存对话时应同时保留检查点目录；删除该目录会失去对应的代码恢复能力。

仅跟踪文件工具产生的版本变更，不保证撤销 Shell、Git、数据库、后台服务或远端 MCP 的副作用，
也不操作 Git 提交、暂存区或分支。Shell 在文件工具前后改变过的已跟踪文件会被当作外部状态处理，
不能将部分文件的恢复称为完整仓库或外部系统回滚。
程序和打包检查都会排除 `.task_outputs/`；目标工作区也应忽略该目录，避免把原始代码快照上传。
